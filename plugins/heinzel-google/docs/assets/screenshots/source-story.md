## Source-bound UI surface inventory

- **Entrypoints:** `pyproject.toml` declares both `heinzel.modules` and `heinzel.connected_sources` as `google = "heinzel_google"`. Their shared target is `src/heinzel_google/__init__.py`; inspect its actual registrations rather than inferring surfaces from the entrypoint names. `src/heinzel_google/_module.py` declares `Module("google", ...)`.
- **Plugin feature UI:** `src/heinzel_google/__init__.py` declares the `Google source review` action with `Navigate(path="/?panel=google:source-review")`, the ABI 1 `source-review` view, and the private read-only `source_review` operation on CLI and web. `src/heinzel_google/views/index.js` renders the selected command, native binary, digest, launcher type and limitations. The existing plan uses the declared action from `/`.
- **Core feature UI:** Calendar is a read/write capability provided by `GoogleCalendar` in `src/heinzel_google/__init__.py`; `src/heinzel_google/_calendar.py` implements event reads. The existing `docs/screenshots.toml` identifies the Core footer summary and calendar pane, and `docs/screenshot_fixture.py` supplies their event data. These are Core-rendered feature surfaces using the adapter, not Google Calendar's own interface. Their actual rendering and selectors still require capture-time verification.
- **Operations and generic surfaces:** `src/heinzel_google/__init__.py` declares `info`, `files`, setup, system info, offline health and live connector health; `src/heinzel_google/_sign_in.py` registers sign-in grants. These can contribute to Core operation, setup, information or Doctor experiences, but the supplied plugin source does not establish exact generic routes or capture states for them. The supplied declarations contain no plugin channel or footer contribution; the calendar footer arises from Core's consumption of the calendar capability. Do not infer that `files` or `info` is CLI-only merely from the absence of a plugin view. The existing CLI scenes are additional useful results, not substitutes for the two calendar UI states.
- **Approvals and connected sources:** `src/heinzel_google/__init__.py` conditionally registers `GoogleConnectedReadService`, `GoogleDocumentWrites`, and `GoogleDraftAppends` only when the host contracts and captured-source loader are available. `src/heinzel_google/_connected_calendar.py` describes separately approved reads; `src/heinzel_google/_document_write.py` describes host-owned review and approval. Core may render related approval flows, but these files and the fixture do not establish a capturable approval screen or successful live write. The connected-calendar module's 'unregistered' docstring conflicts with the conditional registration in `__init__.py`; treat the actual host-dependent availability as unresolved until verified.
- **External provider UI:** Google OAuth and Google Workspace screens are external provider surfaces, not plugin or Core screens. `README.md` describes browser sign-in; the fixture explicitly refuses it. No such screen belongs in this plan.
- **Terminal results:** `files` is a real operation, while `showcase.notes` and `showcase.message_content` and their Rich renderers are declared only in `docs/screenshot_fixture.py`. Their terminal captures are labeled accordingly; no terminal output is presented as feature UI.

## Privacy pitfalls and acceptance

Review every image and transcript independently for real names, addresses, account identities, paths, hostnames, tokens, URLs, document contents and other unexpected data. Apply only the stated verified mappings; fail on unknown identities rather than guessing. Source-review paths and digests are sensitive to the actual selected source, and fixture isolation alone is not privacy acceptance.

Accept only genuine Core or plugin captures with the planned fictional content; reject forged HTML, duplicate captures and caption-only changes. Confirm both calendar states are useful and distinct, the source-review caveat remains visible, and light and dark appearances are actually applied. Verify all commands finish and show their intended results, especially both `files` parameter cases; do not claim filtering from the fixture's fixed response. Verify the fixture-only provenance of the three showcase commands and do not imply live Google, sign-in, write, or approval acceptance.
