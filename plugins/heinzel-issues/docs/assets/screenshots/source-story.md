## Audience
People considering Issues who want to report a problem or request and follow it through to release; maintainers need to know that a writable Beads database is currently required for the built-in tracker. Installation is optional. See `README.md` and the `tool.heinzel.catalog` declarations in `pyproject.toml`.

## Outcome
Show the reassuring journey from a plain-language report to a visible state and release, with a command-line view for people who prefer it. The gallery uses the real plugin view and Core surfaces with fictional data; it does not claim that a report was actually submitted.

## Scenes
1. **Issues page, light:** Three fictional reports show Received, Being worked on, and Released in 0.9.27, alongside the composer. This shows the central value at a glance.
2. **Report history, light:** Open the fictional weather report to reveal its description, attachment name, and dated history through release. This is a meaningful expanded state of the same real view.
3. **Today, dark:** Show the fictional open reports in the Core Today widget. The completed report is absent, demonstrating the widget's useful filter.
4. **CLI list:** Show `hz issues list` with the same fictional reports and plain states. This is a genuine CLI result, not a substitute for the feature UI.

## Privacy pitfalls
Normal presentation fictionalization is explicitly limited to verified owning-interpreter paths becoming `/demo-profile/.venv`, and only the verified whole hostname detail in the genuine Doctor row becoming `demo-host`. These mappings change no SDK health status or remaining detail and establish no privacy acceptance. Unknown identities still fail, and independent review must inspect every image and transcript. Also check paths, account names, report text, attachment names, terminal output, notices, and any Core chrome for real data before publication; a fictional fixture alone does not prove the surrounding capture is private.
